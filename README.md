# DocuLens API

Backend for **DocuLens**: ask questions in natural language across your PDFs and other documents, chat logs (WhatsApp, Telegram, Teams exports, or a live Telegram connection), public web links and connected PostgreSQL databases. Answers cite their sources.

Retrieval is hybrid — BM25 keyword search plus FAISS vector search — and answers are generated by Gemini. The frontend is [`chat-ui`](https://github.com/krisnasetyadi/doculens-ui) (Next.js), the only client of this API.

## How it works

```
chat-ui (Next.js) ──HTTP──▶ FastAPI  /api/v1/*
                              │
                 router/  ── reads the request, calls ──▶  services/<domain>
                              │
              services/rag/   intent → routing → BM25 + FAISS per source → answer (Gemini)
                              │
      PostgreSQL (users, sessions, collections, billing)   Supabase Storage (files + FAISS indexes)
```

- **Upload**: a file is parsed (PDF, DOCX, XLSX, CSV, TXT, PPTX, legacy .doc via antiword), chunked, embedded with `paraphrase-multilingual-MiniLM-L12-v2` and saved as a FAISS index. Files and indexes go to Supabase Storage; `data/` on disk is only a local cache.
- **Ask**: `POST /api/v1/agnostic/query` decides what the question needs (small talk, help, retrieval), searches the selected sources with BM25 and FAISS, merges the results and asks the LLM for an answer with citations.
- **Accounts and billing**: JWT auth with roles, per-plan token quotas and storage limits, Stripe test-mode checkout.

## Repository layout

The root holds only `main.py`, `config.py`, `models.py` and `db.py`.

```
router/              routes only, one file per API domain
services/<domain>.py the logic behind each router (auth, sessions, upload, chat, collections, ...)
services/billing/    plans, quotas, ledger, allocation, Stripe payments
services/rag/        the RAG engine: processor.py composes one mixin per concern
                     (routing, indexes, document/chat/public-link/structured-data search,
                     hybrid, answer, llm, gap_check); conversation/, efficient_mode/, index_cache.py
services/storage/    Supabase Storage + collection rows, storage limits, app database
services/ingest/     text extraction and indexing, chat parsing, upload progress
services/security/   SSRF guard, Telegram session encryption
schema/              table creation, run once at startup
migrations/          SQL to run once in Supabase (see .env.example)
scripts/             sync_hf.py, contract and performance snapshots, backfills
tests/               unit and API tests
```

Rules for where code goes, and the route naming convention, are in [AGENTS.md](AGENTS.md).

## API

All routes live under `/api/v1`, one base path per domain. Interactive docs: `/docs` on a running server.

| Prefix | What it covers |
|---|---|
| `/auth` | register, login, profile, password, admin user management |
| `/agnostic/query` | ask a question across any mix of sources |
| `/sessions` | chat history |
| `/pdf-collections` | document collections: list, upload (file, URL, Google Drive folder), activate, move, delete |
| `/chat-collections` | chat log collections: upload, preview, messages, activate, delete |
| `/telegram-connections` | live Telegram connection: connect, dialogs, sync, history range, remove a synced chat |
| `/public-links` | web pages as a source |
| `/database-connections` | user-connected PostgreSQL databases |
| `/source-folders` | folders for organising sources |
| `/skills` | uploaded skill instructions |
| `/analysis/gap-analysis` | reference-framework gap analysis runs and exports |
| `/payments` | plans, Stripe checkout, token usage and allocation, storage usage |
| `/models/available` | LLMs a query may choose from |

`GET /health` reports database status and collection counts.

## Running locally

Requirements: Python 3.11, PostgreSQL (local, Neon or Supabase).

```bash
python -m venv venv
venv\Scripts\activate            # Windows; source venv/bin/activate elsewhere
pip install torch==2.7.0 --index-url https://download.pytorch.org/whl/cpu   # skips the CUDA build
pip install -r requirements.txt

cp .env.example .env             # then fill in DATABASE_URL, JWT_SECRET, GEMINI_API_KEY
uvicorn main:app --reload --port 8000
```

Tables are created at startup. Supabase Storage (`SUPABASE_URL`, `SUPABASE_SERVICE_KEY`) is optional locally: without it files stay on local disk. Telegram, Stripe and the other optional settings are documented in `.env.example`.

The first account to register becomes the admin.

## Tests

```bash
python -m unittest discover -s tests -t .
```

Tests need a PostgreSQL database in `DATABASE_URL`; each test that touches SQL runs in its own throwaway schema. Gemini, Supabase Storage, Stripe, Telegram and outside HTTP calls are faked. GitHub Actions runs the suite on every push (`.github/workflows/tests.yml`).

## Deployment

The API runs on a Hugging Face Space (Docker, CPU, port 7860) from `Dockerfile`.

This repository is the source of truth. Three workflows keep the copies in step:

| Workflow | When | What |
|---|---|---|
| `tests.yml` | every push and PR | runs the test suite against PostgreSQL |
| `mirror-to-hf.yml` | after tests pass on `main` (or run by hand) | copies the code into the Space repo with `scripts/sync_hf.py` and pushes it, which redeploys the Space |
| `mirror-to-org.yml` | every push to `main` | pushes `main` to the organization repository |

One-time setup in **Settings → Secrets and variables → Actions**:

| Name | Kind | Value |
|---|---|---|
| `HF_MIRROR_REPO` | variable | the Space, e.g. `krisnasetyadi/doculens-api` |
| `HF_MIRROR_TOKEN` | secret | Hugging Face access token with write access to that Space |
| `ORG_MIRROR_REPO` | variable | the org repo, e.g. `my-org/doculens-server` |
| `ORG_MIRROR_TOKEN` | secret | fine-grained GitHub PAT, "Contents: Read and write" on that repo only |

A workflow whose variable is not set skips itself. To sync the Space by hand instead: `python scripts/sync_hf.py --write --target <path to Space checkout>`, then commit and push there.

The Space's runtime settings (database URL, keys) are set as Space secrets on Hugging Face, using the same names as `.env.example`.

## Main settings

| Variable | Default | Purpose |
|---|---|---|
| `DATABASE_URL` | — | PostgreSQL connection string |
| `JWT_SECRET` | — | signs login tokens; required |
| `GEMINI_API_KEY` | — | LLM for answers |
| `GEMINI_MODEL` | `gemini-flash-latest` | Gemini model |
| `EMBEDDING_MODEL` | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` | embeddings |
| `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` | — | file and index storage |
| `CORS_ORIGINS` | `*` | allowed frontend origins, comma separated |
| `CHUNK_SIZE`, `CHUNK_OVERLAP` | `500`, `50` | document chunking |
| `INDEX_CACHE_MAX_BYTES` | 512 MB | memory budget for loaded FAISS indexes |

The full list, with comments, is in `.env.example`.
